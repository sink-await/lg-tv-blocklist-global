# Endpoint certificates

TLS evidence for the 265 region-prefixed and 65 datacentre-cluster entries in
these lists: 327 of 330 have a live service answering on port 443 that presents
a certificate valid for that exact hostname. The three exceptions are named
below.

All of it is public data. DNS records are queryable by anyone, and a TLS
certificate is what a server presents to every client that connects. Nothing
here required access to an LG account, a device, or anything privileged.

Regional endpoints verified **2026-09-12**, cluster endpoints **2026-09-13**. See [docs/verification.md](docs/verification.md) for the
separate DNS-level health check of every entry, generated by
`scripts/verify.py`.

## Why this exists

The regional entries in these lists are generated, not observed: one audited
German host is cross-producted across 49 country codes (see
[CONTRIBUTING](CONTRIBUTING.md#region-coverage)). That raises a fair question —
are those generated names real, or just plausible strings?

There are three grades of evidence, and it is worth being precise about which
one any given entry has:

| Grade | Claim | Coverage |
|---|---|---|
| 1. DNS resolves | A record exists for this name | 330/330 |
| 2. Live LG-controlled TLS service | Something answers on 443 with a certificate LG controls, valid for this name | **327/330 — this document** |
| 3. Traffic observed | A real TV in that market queried it | `de.` and the audited `eic.` hosts only |

Grade 2 rules out two things grade 1 cannot: a stale DNS record pointing at
decommissioned infrastructure, and the name being parked or held by a third
party. It does **not** establish grade 3. Proving that a TV in Brazil contacts
`br.nextlgsdp.com` requires a TV in Brazil; no amount of probing substitutes for
it, which is why regional query logs are the most valuable contribution anyone
can make here.

## Results

265 of 265 endpoints presented a certificate valid for the queried name.

| Match | Count | How |
|---|---|---|
| SAN wildcard | 214 | `subjectAltName` contains `*.<parent>` |
| SAN exact | 2 | `subjectAltName` contains the exact host |
| CN wildcard | 49 | No SAN DNS entries; `CN` contains `*.<parent>` |

The 49 CN-only matches are the whole `lgtvsdp.com` family. Modern TLS clients
require SAN and ignore CN, so those certificates would fail a browser's
hostname check — but for provenance they are the *strongest* evidence in the
set, because they are issued by LG itself rather than by a public CA:

```
subject=C=KR, ST=South Korea, L=Seoul, O=LG Electronics Inc.,
        OU=Digital TV Research Lab., CN=*.lgtvsdp.com
issuer=LG Electronics Inc.
```

## Reproducing this

Resolution goes over DNS-over-HTTPS on purpose. If you run a DNS blocker — and
if you are reading this, you do — a normal lookup returns your own sinkhole for
these exact names, so every endpoint would look dead. A VPN can make it worse:
the VPN client captures DNS into its tunnel, so even an explicitly pinned resolver
becomes unreachable. Port 443 sidesteps both.

```sh
# 1. resolve over DoH, bypassing any local blocker or port-53 redirect
ip=$(curl -s "https://dns.google/resolve?name=br.nextlgsdp.com&type=A" \
     | grep -oE '"data":"[0-9.]+"' | head -1 | cut -d'"' -f4)

# 2. handshake with the IP, sending SNI, and read the certificate
openssl s_client -connect "$ip:443" -servername br.nextlgsdp.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -ext subjectAltName
```

Check the name is covered by `subjectAltName`, or by `CN` for the
`lgtvsdp.com` family. For the DNS-only half of this — every entry, not just the
regional ones — run `python scripts/verify.py --cross-check`.

A negative control matters before trusting any of it: `zz.`, `qq.` and `xj.`
against each family all return NXDOMAIN, so these zones carry no wildcard DNS
record that would make any invented name appear to resolve.
